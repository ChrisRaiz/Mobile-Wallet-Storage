Mobile Wallet Storage

An example website that lets visitors save digital cards, such as memberships, loyalty cards, and event passes, to Apple Wallet or Google Wallet in one tap. It's built with Next.js and signs each pass on the server in the platform's official format.

1Overview

Businesses hand customers cards they need to keep: memberships, loyalty cards, tickets, and gift cards. Phones can store these in a wallet app, where they're always one tap away and can show a barcode or QR code for scanning.

Mobile Wallet Storage is an example of how a website can offer that. A visitor chooses a card and taps a button, and the site produces a pass the phone's wallet app accepts:

  1. The visitor picks a card and taps "Add to Apple Wallet" or "Add to Google Wallet".
  2. The server builds the pass, filling in the visitor's details such as name, member number, and barcode.
  3. The server signs it. Apple and Google both require passes to be signed with keys issued to the business, so phones can trust where they came from.
  4. The phone saves it. iPhone shows an "Add" prompt for the pass file, and Android opens Google's "Save to Wallet" screen.
Try it on your computer: the app runs locally, and npm run demo:setup creates test credentials so both wallet buttons work without Apple or Google accounts. See Run the local demo. Saving a pass on a real phone needs your own credentials (see Configuration).

3Run the local demo

The app runs on your own computer, and one command sets it up so every part works, with no Apple or Google accounts needed. You need Node.js 20.9 or later, plus openssl and unzip, which come with macOS and most Linux systems. On Windows, use Git Bash or WSL.

  1. Clone the repo and move into the app folder:
    bash
    git clone https://github.com/ChrisRaiz/Mobile-Wallet-Storage.git
cd Mobile-Wallet-Storage/mobile-wallet-storage
  2. Install the dependencies. Run this again whenever you pull new changes, since updates can add or upgrade packages:
    bash
    npm install
  3. Create the demo credentials. This makes a throwaway test certificate authority, a Pass Type ID certificate it issues, and a test signing key for Google, and saves them in .env.local, which git ignores:
    bash
    npm run demo:setup
  4. Start the app:
    bash
    npm run dev
  5. Open http://localhost:3000, pick a card, type a name, and try both buttons.

Why the pass won't open in a wallet: Apple Wallet and Google Wallet only accept passes signed with credentials they issued. The demo's passes are built and signed exactly the same way, but with test credentials, so a phone or Mac will refuse them. To save a card for real, swap in your own credentials (see Configuration).

Look inside the Apple pass

A .pkpass file is a zip archive, so you can open the one you downloaded and check its signature yourself. From the app folder:

bash
unzip -o ~/Downloads/example-club.pkpass -d pass-check
cat pass-check/pass.json

You'll find pass.json, the icon and logo images, manifest.json with a SHA-1 hash of each file, and the signature made from that manifest.

4How wallet passes work

Both platforms start from the same idea, a card with fields and a barcode, but they deliver it to the phone in different ways.

Apple Wallet

An Apple Wallet pass is a .pkpass file: a zip archive with these files inside.

FilePurpose
pass.jsonThe pass type, its fields, colors, and barcode
icon.png, logo.pngImages shown on the pass and in notifications. The icon is required.
manifest.jsonA SHA-1 hash of every other file in the pass
signatureA signature of the manifest, made with the Pass Type ID certificate

A membership card would use the storeCard style. A trimmed-down pass.json:

pass.json
{
  "formatVersion": 1,
  "passTypeIdentifier": "pass.com.example.membership",
  "teamIdentifier": "ABCDE12345",
  "serialNumber": "0042-1187",
  "organizationName": "Example Club",
  "description": "Example Club membership card",
  "storeCard": {
    "primaryFields": [{ "key": "member", "label": "Member", "value": "Jordan Lee" }]
  },
  "barcodes": [{
    "format": "PKBarcodeFormatQR",
    "message": "0042-1187",
    "messageEncoding": "iso-8859-1"
  }]
}

The server sends the finished file with the content type application/vnd.apple.pkpass. Safari on iPhone recognizes it and shows the pass with an Add button.

Google Wallet

Google Wallet stores passes on Google's side. Each pass is an object (one visitor's card) that belongs to a class (the shared design for every card of that kind). To save one, the server puts the class and object in a JSON Web Token (JWT), signs it with a Google Cloud service account key, and sends the visitor to the save link. Google creates both when the card is saved.

JWT payload
{
  "iss": "wallet@your-project.iam.gserviceaccount.com",
  "aud": "google",
  "typ": "savetowallet",
  "payload": {
    "genericClasses": [{ "id": "ISSUER_ID.membership" }],
    "genericObjects": [{
      "id": "ISSUER_ID.member-0042-1187",
      "classId": "ISSUER_ID.membership"
    }]
  }
}
save link
https://pay.google.com/gp/v/save/<signed JWT>

Opening the link on Android shows the card with a Save button. A full object would also include the card's header, fields, barcode, and colors.

Apple and Google both publish official "Add to Wallet" button artwork and usage guidelines. Before going live, swap the app's plain buttons for those official badges.

5How the app works

The page is a Next.js server component that checks which platforms have credentials. Only a yes or no for each platform is sent to the browser, never the keys. The card picker, name field, and live preview run in the browser. Both buttons are plain links to two route handlers that build and sign passes on the server.

RouteReturns
GET /api/passes/appleA signed .pkpass file, as application/vnd.apple.pkpass
GET /api/passes/googleA 302 redirect to the signed Save to Google Wallet link
Either route with &format=jsonThe unsigned pass data, even in demo mode
example
/api/passes/apple?card=membership&name=Jordan%20Lee

card is membership, loyalty, or event. The name is checked in the browser and again on the server: 1 to 40 letters, spaces, apostrophes, periods, or hyphens.

StatusWhen
400Unknown card or invalid name. The response says what's wrong.
503That platform has no credentials. The response lists the missing settings.
500Signing failed, usually because a certificate or key is wrong. Details go to the server log.

Every pass gets a card number derived from the card type and name. The preview and the pass always show the same number, and saving the same card again updates one Google Wallet pass instead of adding a second.

6Configuration

Real passes can only be issued with accounts from each platform. None of these are part of the repository.

PlatformYou need
Apple WalletAn Apple Developer Program membership, a Pass Type ID registered to it, and that Pass Type ID's signing certificate, plus Apple's WWDR intermediate certificate
Google WalletA Google Wallet API issuer account (from the Google Pay & Wallet Console), and a Google Cloud service account with a key, linked to the issuer account

To use real credentials instead of the demo ones, copy .env.example to .env.local (replacing the demo file) and fill in the values. Each platform turns on as soon as all of its required values are set. Restart the app after changing .env.local.

VariableValue
APPLE_PASS_TYPE_IDYour Pass Type ID, such as pass.com.yourcompany.membership
APPLE_TEAM_IDYour 10-character Apple Team ID
APPLE_WWDR_CERTApple's WWDR intermediate certificate
APPLE_SIGNER_CERTYour Pass Type ID certificate
APPLE_SIGNER_KEYThe private key for that certificate
APPLE_SIGNER_KEY_PASSPHRASEOptional. Only if the key is encrypted.
GOOGLE_ISSUER_IDYour numeric Google Wallet issuer ID
GOOGLE_SERVICE_ACCOUNT_EMAILclient_email from the service account key file
GOOGLE_PRIVATE_KEYprivate_key from the service account key file
PUBLIC_SITE_URLOptional. The site's public HTTPS address, so Google Wallet can load the card logo.

Certificates and keys can be pasted as PEM text with \n line breaks, or as base64 of the whole PEM file.

Keep keys secret: certificates, private keys, and service account files must never be committed. .env.local is already in .gitignore. When hosting, set them in your host's environment settings. The pass routes sign on the server, so the app needs a Node.js host such as Vercel rather than static hosting.

7Testing

Real credentials can't live in a public repository, so the tests create stand-ins each run: a throwaway certificate authority in place of Apple's, a signer certificate it issues, and an RSA key pair in place of a Google service account key. They then build real passes and check them with tools that are independent of the app.

npm test
