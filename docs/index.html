Mobile Wallet Storage

An example website that lets visitors save digital cards, such as memberships, loyalty cards, and event passes, to Apple Wallet or Google Wallet in one tap. It's built with Next.js and designed around each platform's official wallet API.

  • 2wallet platforms
  • 1card, saved either way
  • Next.js 14with TypeScript

1Overview

Businesses hand customers cards they need to keep: memberships, loyalty cards, tickets, and gift cards. Phones can store these in a wallet app, where they're always one tap away and can show a barcode or QR code for scanning.

Mobile Wallet Storage is an example of how a website can offer that. A visitor chooses a card and taps a button, and the site produces a pass the phone's wallet app accepts:

  1. The visitor picks a card and taps "Add to Apple Wallet" or "Add to Google Wallet".
  2. The server builds the pass, filling in the visitor's details such as name, member number, and barcode.
  3. The server signs it. Apple and Google both require passes to be signed with keys issued to the business, so phones can trust where they came from.
  4. The phone saves it. iPhone shows an "Add" prompt for the pass file, and Android opens Google's "Save to Wallet" screen.
Planned design: sections 4 to 6 describe how the integrations are designed to work. They aren't in the code yet. See Project status.

3Getting started

You need Node.js 18.17 or later and npm. The app lives in the mobile-wallet-storage folder inside the repository.

  1. Clone the repo and move into the app folder:
    bash
    git clone https://github.com/ChrisRaiz/Mobile-Wallet-Storage.git
cd Mobile-Wallet-Storage/mobile-wallet-storage
  2. Install the dependencies and start the development server:
    bash
    npm install
npm run dev
  3. Open http://localhost:3000. The page reloads as you edit files in src/app/.
ScriptWhat it does
npm run devStarts the development server with live reload
npm run buildBuilds the app for production
npm startServes the production build
npm run lintChecks the code with ESLint

4How wallet passes work

Both platforms start from the same idea, a card with fields and a barcode, but they deliver it to the phone in different ways.

Apple Wallet

An Apple Wallet pass is a .pkpass file: a zip archive with these files inside.

FilePurpose
pass.jsonThe pass type, its fields, colors, and barcode
icon.png, logo.pngImages shown on the pass and in notifications. The icon is required.
manifest.jsonA SHA-1 hash of every other file in the pass
signatureA signature of the manifest, made with the Pass Type ID certificate

A membership card would use the storeCard style. A trimmed-down pass.json:

pass.json
{
  "formatVersion": 1,
  "passTypeIdentifier": "pass.com.example.membership",
  "teamIdentifier": "ABCDE12345",
  "serialNumber": "0042-1187",
  "organizationName": "Example Club",
  "description": "Example Club membership card",
  "storeCard": {
    "primaryFields": [{ "key": "member", "label": "Member", "value": "Jordan Lee" }]
  },
  "barcodes": [{
    "format": "PKBarcodeFormatQR",
    "message": "0042-1187",
    "messageEncoding": "iso-8859-1"
  }]
}

The server sends the finished file with the content type application/vnd.apple.pkpass. Safari on iPhone recognizes it and shows the pass with an Add button.

Google Wallet

Google Wallet stores passes on Google's side. Each pass is an object (one visitor's card) that belongs to a class (the shared design for every card of that kind). To save one, the server puts the object in a JSON Web Token (JWT), signs it with a Google Cloud service account key, and sends the visitor to the save link.

JWT payload
{
  "iss": "wallet@your-project.iam.gserviceaccount.com",
  "aud": "google",
  "typ": "savetowallet",
  "payload": {
    "genericObjects": [{
      "id": "ISSUER_ID.member-0042-1187",
      "classId": "ISSUER_ID.membership"
    }]
  }
}
save link
https://pay.google.com/gp/v/save/<signed JWT>

Opening the link on Android shows the card with a Save button. A full object would also include the card's header, fields, barcode, and colors.

Apple and Google both publish official "Add to Wallet" button artwork and usage guidelines. The site should use those badges rather than custom buttons.

5Planned design

The wallet work is planned as two Next.js route handlers, so signing keys stay on the server and never reach the browser.

Planned routeReturns
GET /api/passes/appleA signed .pkpass file for the chosen card
GET /api/passes/googleA redirect to the Google Wallet save link for the chosen card

The home page would list the available cards, each with both "Add to Wallet" buttons pointing at these routes. Card details are passed as query parameters, then validated on the server before any pass is built.

Not built yet: route names and behavior may change as the integrations are implemented.

6Accounts and keys

Real passes can only be issued with accounts from each platform. None of these are part of the repository.

PlatformYou need
Apple WalletAn Apple Developer Program membership, a Pass Type ID registered to it, and that Pass Type ID's signing certificate, plus Apple's WWDR intermediate certificate
Google WalletA Google Wallet API issuer account (from the Google Pay & Wallet Console), and a Google Cloud service account with a key, linked to the issuer account
Keep keys secret: certificates, private keys, and service account files must never be committed. Store them as environment variables or in your host's secret manager.
